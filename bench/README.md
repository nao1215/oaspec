# Benchmarks

oaspec is measured the way a user runs it, one escript process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds the escript (`gleam build` and `gleam run -m gleescript`, as release.yml does), runs each command in interleaved rounds, and reports latency, CPU time, peak RSS and, for the large documents, throughput in operations per second.

```console
$ go install github.com/nao1215/himorime@latest
$ just bench            # himorime run bench
$ just bench-compare    # himorime compare --against main bench
```

The escript runs on the Erlang runtime and `generate` runs `gleam format` on what it writes, so `escript` and `gleam` must be on PATH; `mise install` provides both, and the justfile puts them on PATH.

## Regression suite: himorime.yaml

`just bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v0.70.0 just bench-compare` compares against another revision. `himorime run --filter '^generate 500$' bench` measures one benchmark, and `himorime run --tag smoke bench` only the small ones.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

oaspec works on one OpenAPI document per call, so the number in a benchmark name is the number of operations in the document. The documents are generated by `gen.sh` before measuring, so no fixture is added, and both revisions run the working tree's `gen.sh`. Every two operations share one resource: a GET with a query parameter and an array response, and a POST with a JSON request body, over component schemas with an enum, a required list, an array and a shared `$ref`.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `oaspec version` | starting the escript on the BEAM |
| `validate 10` | `validate` | parsing and checking a small document, where start-up dominates |
| `validate 500` | `validate` | parsing, resolving and checking a document of 500 operations |
| `generate 10` | `--mode` both, server, client | generating and formatting a small package |
| `generate 500` | `--mode` both, server, client | generating and formatting the code of 500 operations |
| `generate check 500` | `generate --check` | the drift check a CI job runs: generating in a temporary directory and comparing with the files on disk |
| `validate error` | `validate` on a document without `info` | the failing path, exit 1 |

`oaspec init` is not measured: it writes a fixed file and does no work that grows with anything. Documents with external `$ref` files and the full GitHub and Stripe documents are covered by the integration tests, not measured here; the Stripe and GitHub documents are downloaded at test time, and the suite does not go to the network.

Numbers from different machines are not comparable; compare revisions on one machine, as `just bench-compare` and CI do.
